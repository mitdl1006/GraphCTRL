# 알려진 문제

게이트 항목이 수정 3회 후에도 실패하면 재현 절차와 함께 기록한다.

## 솔버 드래그 속도가 목표에 못 미침 (2026-11-16)

- 목표: 미지수 100개인 성분에서 드래그 한 프레임 4 ms 이하.
- 측정(샌드박스 4코어, dev 프로필에서 솔버 크레이트는 opt-level 3): 미지수 50개 1.0 ms, 100개 6.5 ms, 300개 215 ms.
  첫 풀이는 0.5 ms / 3.0 ms / 84 ms, 이미 풀린 상태의 재풀이(진단 포함)는 0.1 ms / 0.5 ms / 11.5 ms.
- 재현: `cargo test -p gc_solver --test perf -- --ignored --nocapture`
- 영향: 점 50개가 서로 구속으로 이어진 큰 스케치 덩어리를 끌 때 60 fps를 못 낸다. 보통 크기의 스케치(미지수 수십 개)는 문제없다.
- 원인: 밀집 행렬 QR을 프레임마다 여러 번 하고, 피벗 QR이 단계마다 열 노름을 다시 계산한다.
- 개선 여지: 열 노름 갱신(downdating), 프레임당 QR 재사용, 성분을 더 잘게 나누는 그래프 분해. 드래그는 이미 잡힌 성분만 푼다.

## 메시 파일은 UI 스레드에서 읽고 올린다

설비 메시(STL)를 불러올 때 파일 읽기·정점 병합·GPU 업로드가 그 프레임 안에서 돈다. 수십만 삼각형 파일은 불러오는 순간
화면이 잠깐 멈춘다(그 뒤 프레임은 정적 버퍼를 다시 쓰므로 영향 없음). 계획(5.2): 작업 스레드에서 읽고 프레임당 예산으로
나눠 올리기. 문서에는 파일의 절대 경로가 들어가므로 다른 PC로 옮기면 파일을 찾지 못한다(상대 경로 + 해시로 바꿀 예정).


## [해결됨 ba5caa9] 구속이 많은 셀을 만들 때 관계 추가 시간이 급격히 늘어남 (QA, 2026-11-17)

- **해결(백엔드 ba5caa9, 리드 확인)**: 솔버가 관계로 묶인 자유 컴포넌트 섬별로 풀고 이미 만족된 섬은 건너뜀 → 관계 하나 추가 시 그 섬만 다시 풂. `bench_scene --components 1000` 셀 구성 전체 약 0.15 s(이전 5분+), 프레임 p95 1000개 3.8 → 1.7 ms(`component_statuses()` 리비전별 캐시). 회귀 테스트 `gc_session/tests/relation_scale.rs`.

- 측정(release, `target/release/examples/bench_scene`, 샌드박스 4코어): 구속으로 이어진 컴포넌트 50개 0.02 s, 100개 0.06 s, 200개 0.6 s,
  **400개 9.5 s**, 1000개는 5분 안에 끝나지 않음(셀을 만드는 동안 관계를 하나 추가할 때마다 전체를 다시 풀어 개수에 대해 3제곱에 가깝게 늘어남).
- 프레임 단위 조회(`bench_scene`의 표)는 200개에서도 p95 0.6 ms로 예산(2 ms) 안이다 — 느린 것은 **관계를 추가·편집하는 순간**이다.
- 영향: 수백 개 구성요소를 구속으로 엮는 큰 어셈블리에서 구속 추가 한 번이 수 초. dev 프로필은 더 느리다.
- 개선 여지: 관계 추가 시 영향받는 연결 성분만 다시 풀기(그래프 분해), 이전 해를 초기값으로 쓰기, 일괄 추가 API.
- 재현: `cargo build --release -p gc_session --example bench_scene` 후 `target/release/examples/bench_scene --components 400 --frames 5`의 총 시간.

## 구속이 사슬로 이어진 컴포넌트를 만들 때 시간이 폭발적으로 늘어남 (QA, 2026-11-17, 리드 ba5caa9 이후)

- 앞의 "관계 추가 시간" 항목(각각 따로 고정 부품에 매인 컴포넌트 수백 개)은 리드 ba5caa9 이후 `bench_scene` 기준 800개에서도 문제없다(블록킹 13 ms).
  **그러나 컴포넌트가 사슬로 쌓이는 경우**(1번 위에 2번을 Mate, 2번 위에 3번을 Mate, …)는 여전히 급격히 느려진다.
- 측정(`cargo test -p gc_session --test qa_selection_frames -- --ignored --nocapture relationship_build_times`, 샌드박스, 테스트 프로필):
  5개 0.3 ms · 10개 3.8 ms · 15개 18 ms · 20개 55 ms · 25개 146 ms · **30개 426 ms** — 5개 늘 때마다 약 3배(다항식보다 빠른 증가).
  50개 사슬은 수 분 이상 걸리는 것으로 보이며(10분 이상 걸려 중단함) 사실상 만들 수 없다.
- 영향: 부품을 차곡차곡 쌓아 구속하는 일반적인 어셈블리(수십 단)에서 구속 추가 한 번이 멈춘 것처럼 보인다.
- 원인 후보: 연결된 컴포넌트 전체를 한 번에 최소제곱으로 푸는 `solve_relationships`(`gc_doc/src/relate.rs`)에서 사슬의 길이에 따라 반복·야코비안 비용이 늘고, 새 관계를 추가할 때마다 이전 해를 초기값으로 쓰지 못함.
  사슬은 위상 순서대로 한 컴포넌트씩 풀 수 있다(고정 쪽부터).
- 재현은 위 명령. 수정 뒤에는 30개 사슬이 수 ms로 내려가야 하고, 100개 사슬을 만드는 테스트를 추가할 수 있다.

## 스케치 직사각형 패턴이 요소 수에 따라 급격히 느려짐 (QA, 2026-11-17)

- 측정(`cargo test -p gc_session --test qa_sketch_shapes -- --ignored --nocapture pattern_times`, 샌드박스, 테스트 프로필): 3×3 = 9개 4 ms · 5×5 = 25개 86 ms ·
  8×8 = 64개 2.1 s · **10×10 = 100개 11.5 s** · 12×12 = 144개 47 s(요소 수가 1.4배 늘 때 4배). 60×60 = 3600개는 10분 안에 끝나지 않았다.
- Inventor의 스케치 패턴은 500×500까지 허용하는데(`gc_doc`도 개수 2~500을 받아들임) 사실상 10×10 격자도 한참 걸린다. 구멍 격자 같은 흔한 작업에서 멈춘 것처럼 보인다.
- 원인 후보: 패턴의 모든 복사본이 원본과의 구속(같은 길이·평행 등)으로 한 연결 성분이 되어 밀집 QR을 프레임마다 푸는 비용(위 "솔버 드래그 속도" 항목과 같은 뿌리).
  복사본을 원본에서 직접 계산한 위치로 만들고 "고정 패턴" 구속만 두거나, 성분을 원본별로 분해하면 선형에 가깝게 된다.
- 담당: 백엔드(`gc_doc/src/command.rs` `RectangularPattern`/`CircularPattern`, `gc_solver`). 수정 후 10×10이 수십 ms 안에 끝나는지 위 보고 테스트로 확인.
