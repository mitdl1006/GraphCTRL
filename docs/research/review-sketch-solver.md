# Plan review: sketching and constraint solver

## 1. [BLOCKER] 5.4 item 7 (drag) + Appendix C F16/F17

**Problem.** The drag objective is under-determined and has no algorithm, so F16 cannot pass as written. The plan says only: satisfy the constraints while minimising |grabbed - cursor|^2 (exact pin). Pinning one vertex of a free triangle (3 DOF) leaves one DOF (rotation about the grabbed point) undecided. The natural tie-break (minimum-norm step from the previous frame) is still path dependent. I reran the review's experiment (numpy, stdout only): triangle (0,0),(10,0),(0,10) with three lengths, vertex A dragged round the F16 loop. Exact pin + previous-frame tie-break: net rotation 4.51 / 7.05 / 7.05 deg for 4 / 64 / 512 samples. Exact pin + tie-break anchored at the drag-start state: 0.0000 deg in all three, lag 1e-16. F16 demands 0 deg. Also missing: the sub-step size (review: 1/4 of the smallest involved length), and what is grabbed when the user picks a line body or a circle rim. 'Refuse to grab zero-mobility parameters' as written refuses a line with one fixed endpoint, which Inventor lets rotate.

**Fix.** Rewrite 5.4-7 as follows. (a) Grab kinds: Point(p): target p = cursor. LineBody / ArcBody: each mobile endpoint target = its drag-start position + (cursor - cursor_at_begin). CircleRim / ArcRim: target (|cursor - c| - r) = 0. (b) begin_drag drops grabbed parameters whose mobility < 1e-6 and returns DragRefused only when none remain. (c) Each update solves lexicographically: L1 all constraints g(x)=0; L2 min |T(x) - target|^2; L3 min |x - x_start|^2, where x_start is the state at begin_drag, never the previous frame (auxiliary unknowns excluded from the L3 norm). (d) Algorithm per iteration: pivoted QR of J^T gives rank and null basis N; d_r = -J^+ r; z1 = min-norm least squares of (dT/dx) N z = target - T(x + d_r); N2 = null((dT/dx) N); z2 = least squares of N N2 z2 = x_start - (x + d_r + N z1); step = d_r + N z1 + N N2 z2, with backtracking on max|r|. Warm start from last_good. (e) Sub-step the cursor so each sub-target moves <= 1/4 of the smallest entity length in the grabbed component (floor 1e-3 S). (f) Frame scale S, per-constraint scales and the orientation signature are frozen at begin_drag for the whole session. (g) update returns FrameOutcome::{Moved, Clamped (cursor unreachable, nearest feasible point kept), RolledBack(Flip | NotConverged)}; last_good is unchanged on rollback. (h) F16 asserts net rotation < 1e-9 rad for 4/64/512 samples, lag <= tol, identical samples give identical bits. Add F16b: a line with one fixed endpoint grabbed by its body rotates and is not refused.

## 2. [BLOCKER] 4.2 (commands are data, one Txn per frame), 4.4, 5.1, 5.5 (solver inside the Txn)

**Problem.** Three rules contradict each other for dragging. (1) 5.4 makes the drag an owned typestate Dragging{sys, start, last_good, ..} that must live across frames. (2) 4.2 says every change is a serde Command applied once per frame in a Txn, committed, and recorded in History with a Revision bump. (3) Document fields are private and derived data is a revision-keyed cache. As written, each drag frame becomes its own undo step, and each bumps the Revision, which (4.4) invalidates FK, the collision world, waypoint validation and marks paths stale 60 times per second. A solver session cannot sit inside a Command or the Document, and the plan names no owner for it. The research's 'BeginDrag opens a step, per-frame commits are absorbed' rule (br9p5r4t0 line 144) was dropped from the plan. gc_doc is built in Stage 2, gc_sketch in Stage 3 and gc_tools after it, by different agents, so this interface will be invented three times. There is also a second rollback source of truth (Dragging.start versus the History swap).

**Fix.** Add to 4.2 and 5.5: 'Continuous interactions (sketch drag, and likewise joint-jog sliders and placement gizmos) never commit per frame. Solver sessions are not document state and never appear in a Command.' Concretely: gc_doc defines EditCtx { sessions: BTreeMap<Id<Sketch>, SketchSession> }, owned by gc_app and passed to apply(doc, &Command, &mut EditCtx). SketchSession { structure_rev, state: Idle(System) | Dragging(..) } is rebuilt whenever the sketch's structural revision differs (always after undo, redo, load). Intents: BeginDrag{sketch, grab}, DragTo{cursor}, EndDrag, CancelDrag. BeginDrag and DragTo touch only the session; the document and Revision are unchanged. Readers use one accessor, SketchGeom { sketch: &Sketch, preview: Option<&PreviewCoords> }, so gc_draw, the dimension overlay and measured (driven) values show the preview. EndDrag opens one Txn, writes the final coordinates, commits: exactly one History step. If the final coordinates are bit-identical to the start, nothing is committed (no step, no Revision bump). CancelDrag or Esc drops the session. Tests: a 30-frame scripted drag gives undo depth +1 and Revision +1; Esc restores identical bits; a path's stale flag does not change before EndDrag.

## 3. [MAJOR] 5.4 items 1, 5, 6 (substitution, diagnosis, try_add) and 5.5

**Problem.** Substitution and blame semantics are ambiguous and give wrong answers in cases F1-F20 do not cover. (a) 'Candidate ordered last' is meaningless when the candidate is substituted away. Example: old Distance(A,B)=10, H(AB), then candidate HorizontalDistance(A,B)=7. After the merges the old Distance row has zero gradient and r = -3, so the zero-gradient rule reports the old Distance as the conflicting row, not the candidate. (b) Redundant and Conflicting are stated per constraint, but dependence is per row (review A13, 'partially redundant', a P1 item the plan omits). Example: l1 and l2 both Horizontal, candidate Collinear(l2, l1): its two rows are identical after substitution; one is dependent, yet the constraint removes one DOF and must be accepted. (c) With auxiliary unknowns a row test is wrong: Parallel3 between two lines already along X has one row with a gradient in lambda only; it looks independent but removes no DOF. (d) F15 expects SingularHere but the return type in 5.4-6 is only Added / Redundant / Conflicting, and the witness test is not described. (e) 'Zero-gradient row rule' is named but not defined. A merge of two parameters already in one class (F2) is not covered; only contradictory merges are. (f) Nothing says what happens when a geometric (non-dimension) constraint, or an inferred one, comes back Redundant.

**Fix.** Add to 5.4: (1) Sketch constraints stay first-class Id<Constraint> entities whether or not the solver substitutes them. Every union-find edge and every fixed parameter stores its ConstraintId. All reports use sketch ids: Blame::{Row(ConstraintId, u8), Fixed(..), Merged(ConstraintId)}. (2) Merging two parameters already in one class: offsets equal within tol gives Redundant{with: merge path}, otherwise Conflicting{with: merge path}. (3) Zero-gradient row (max |dr_k/dx| <= 1e-12 in the scaled frame after substitution): Redundant if |r_k| <= tol, else Conflicting; blame = provenance of every fixed or merged parameter the row reads. (4) Dependency { row: (ConstraintId, u8), with: Vec<Blame>, kind: Redundant | Conflicting | PartiallyRedundant | SingularHere }. (5) try_add is defined on DOF, not rows: on a copy, the candidate is never substituted (always explicit rows) and is ordered last. Conflicting if the solve is Inconsistent or any candidate row has |combo| > 1e-7. Otherwise Added if dof_after < dof_before, even when some of its rows are dependent (reported PartiallyRedundant, informational only). If dof_after == dof_before, run the witness test (null-space step of 1e-3 S, re-project, recompute rank): rank increase gives AddedSingular(SingularHere), else Redundant. n includes auxiliary unknowns, so Parallel3 nets out correctly. (6) Any dependency set that contains the candidate is re-rooted so the candidate is the subject. (7) Sketch-level policy: dimension Redundant or Conflicting: prompt 'convert to reference dimension'. Explicit geometric constraint Redundant or Conflicting: rejected with a status-bar message naming the 'with' set, document unchanged. Inferred constraints: each goes through try_add in priority order and is dropped silently unless Added. A property test asserts that no stored sketch ever contains a fully redundant constraint created by a tool.

## 4. [MAJOR] 5.1 (update flow: 'keep the last good solution on failure'), 5.5 (driving flag, expressions, driven dimensions)

**Problem.** The document state after a failed solve is undefined. 5.1 implies the parameter edit is kept while the sketch keeps old coordinates. The document then holds coordinates that violate its own driving dimensions, with no stored or derivable 'unsolved' state (solve reports are caches). Waypoints bound to those points silently keep stale positions and the path is not marked stale: a wrong robot path with no warning. Whether load re-solves is also unstated; if it does, save-then-load is not the identity. Driven dimensions: the plan allows 'other dimension references' in expressions and gives every dimension a d-name, but a driven dimension's value depends on the whole solve of its sketch. A driving dimension that references a driven dimension of the same sketch is an algebraic loop the expression-level cycle check in gc_expr cannot see. Where a driven value lives (document or derived) is unstated. Deleting a dimension another expression references is undefined.

**Fix.** Add invariant I1 to 5.1: 'Every committed sketch satisfies all its driving constraints within tol.' A command whose solve ends Inconsistent, NotConverged or Flipped (after continuation) is rolled back whole by dropping the Txn, including the parameter edit, and returns EditError::SketchUnsolved { sketch, status, blame }. The dimension value box stays open with the inline error; the fx table lists the failing sketches. This is the definition of 'last good solution kept'. Further rules: (1) solve is idempotent: if max|r| <= tol on entry, LM takes no step and coordinates are bit-identical. (2) Load never solves; it runs a non-mutating check() and marks a violating sketch needs_repair (read-only until the user re-solves). (3) Continuation interpolates all changed driving values and external reference positions of one sketch jointly from old to new, halving down to 1/1024. (4) A driven dimension's value is never stored; measure(dim, coords) computes it with the same sign and orientation convention as the driving residual, so converting between driven and driving is stable. (5) Dependency graph nodes are Param, DrivingDim, Sketch, DrivenDim, with edges Sketch <- its driving dimensions and DrivenDim <- its sketch, plus expression references. Any cycle is the inline 'cycle' error. Sketches are solved in topological order inside one Txn. (6) Deleting a dimension or parameter that other expressions reference replaces those references by the current numeric value in the same Txn and logs a notice. Tests: undo of a rejected edit is a no-op; a proptest checks I1 after every command.

## 5. [MAJOR] 5.4 items 2-3, gc_core::Tolerance, Appendix C F18/F19

**Problem.** No numerical value is specified anywhere in the plan: residual tolerance, stationarity test, rank threshold, conflict threshold, degenerate length, nudge size, LM budget and damping, mobility threshold. The review called the rank threshold a judgement call (1e-8 in sketch-solver, 1e-13 in FreeCAD) and asked for an ill-conditioned band; the plan omits the band. The scaled frame is also underspecified: S is undefined (it is 0 for a one-point component), and the transform must treat parameter kinds differently (coordinates are translated and scaled, radii and union-find offsets only scaled, auxiliary t and lambda untouched). Translating a radius would break F18 silently. The nudge is 'along the null space', but null(J) always contains the rigid motions of an ungrounded component. I verified: a free collinear 3-4-5 triangle with no fixed point has rank 2 and a 4-dimensional null space at the stall; a nudge that is a rigid translation (|J t| = 0) stalls again at |r| = 1.15, which would be reported as a false conflict; a generic vector projected onto null(J) solves in 7 iterations. The damping matrix D is unspecified; Marquardt scaling by diag(J^T J) destroys the property that steps stay in range(J^T), so unconstrained geometry would drift.

**Fix.** Add a table 'gc_solver::Tolerances::DEFAULT (scaled frame, S = 1)' to 5.4. S = max(bounding-box diagonal of the component's points including fixed and external ones, largest length-dimension value, 1e-3 m); origin = bounding-box centre. ParamKind::{Coord(axis), Length, Ratio, Angle}: Coord maps to (v - o)/S, Length to v/S, Ratio and Angle unchanged. Values: residual tol 1e-10; stationary when |J^T r|_2 <= 1e-9 |J|_F |r|_2 or the accepted step < 1e-13 while |r| > tol; rank: |R_kk| < 1e-8 |R_11| is dependent, and any pivot ratio in 1e-10..1e-6 lists the constraint in ill_conditioned; combo conflict 1e-7; zero gradient 1e-12; degenerate length 1e-9; mobility 1e-6. LM: D = I, lambda0 = 1e-6, x0.1 on accept and x10 on reject, 50 iterations per continuation stage, unpivoted QR of the stack. Nudge: h_i = SplitMix64(param id) mapped to [-1, 1]; nudge = 1e-3 * normalise(N N^T h), never a single basis vector; one retry; on failure return the pre-nudge coordinates with Inconsistent. Scales frozen at solve start: parallel, perpendicular and symmetric divide by max(|d1|0, |d2|0); the angle residual is min(|d1|0, |d2|0) * atan2(..); Parallel3 divides by |a|0. Angle cut: an error within 1e-12 of +-pi is taken as +pi, and an LM step that changes any angle residual by more than pi/2 is halved. Use libm atan2, sin, cos. Add fixture F4b: the 3-4-5 collinear start with no fixed point must be Solved after the nudge.

## 6. [MAJOR] 5.4 item 4 (orientation signature), 5.4 constraint lists, 5.5 (smart dimension mapping)

**Problem.** The plan never states what each dimension and constraint stores, although branch stability depends entirely on it ('cursor quadrant', 'tangent side', 'radius sign' are mentioned only as words). Specific defects: (a) 'Line-line distance' is defined in the research as parallel + point-line distance. If the lines are already Parallel or both Horizontal, the embedded parallel row is dependent, and the dimension is reported redundant on the most common use (dimensioning the width of a rectangle). (b) 'Corner direction' is in the signature list. If it means the turn sign at any shared endpoint, dragging a free polyline vertex through collinearity is rolled back, which contradicts Inventor behaviour for unconstrained geometry. (c) 'Arc sweep': the review mixes 'sweep half' and 'sweep continuity'; a legitimate drag takes an arc from 170 to 190 deg, so a half-plane test is wrong. (d) Value domains (zero, negative, angle 0 / 180 / 360) are undefined. (e) Dimension annotation position is not in the data model, so placement cannot be saved or undone.

**Fix.** Add a 'stored data' table to 5.5. Every dimension: { id, param: ParamId, source: String, driving: bool, text_pos, kind }. Kinds: Distance{p, q}, value > 0 (0 rejected: 'use Coincident'). HDistance / VDistance{p, q, sign = +-1 captured from (q - p) on that axis at creation; + by id order when |delta| < 1e-9 S}, value > 0. PointLineDistance{p, line, side = +-1}, value > 0. LineLineDistance{l1, l2, side}: exactly one row, the signed distance of l2.a from l1, and no parallel row; smart dimension offers it only when the lines are parallel within 1e-6 rad. Angle{l1, rev1, l2, rev2}: value in (0, 2pi) exclusive, measured counter-clockwise from dir1 to dir2; the cursor quadrant picks (rev1, rev2) so the value at creation is in (0, pi]; 0 and 2pi rejected with 'use Parallel'. Radius / Diameter, value > 0. Constraints: TangentLineCircle{side}, TangentCircleCircle{External | Internal}, EndTangent{smooth = sign of dot(line direction leaving the shared point, arc tangent at that end)}. Negative or zero lengths are an inline error. Signature elements, each guarding only something that is constrained: RadiusSign (r > degenerate for every circle and arc); TangentSide; EndTangent smooth-versus-cusp; DistanceSide for signed dimensions; AngleBranch (measured angle changes by less than pi/2 per accepted sub-step); ArcSweep continuity (|sweep_new - sweep_old| < pi per accepted sub-step, sweep in (1e-9, 2pi - 1e-9)). Delete 'corner direction'. State explicitly: unconstrained geometry has no signature. Add fixtures: a width dimension between two Horizontal lines is Added, not Redundant; a free polyline vertex dragged across the line through its neighbours is Moved; an arc endpoint dragged from 170 to 190 deg sweep is Moved.

## 7. [MAJOR] 5.5 (Sketch { space, points, curves, constraints, dimensions }), 5.1 frame graph, 5.10

**Problem.** The data model cannot express several things the plan promises. (a) 'Projected origin point (fixed)' and '3D sketch snaps to existing sketch points and work points': there is no external-reference entity. A snap to another sketch's point can then only copy coordinates, so the 3D polyline does not follow when the 2D dimension changes, although completion criterion 7 relies on associativity. (b) space: Planar(FrameId) | Spatial: a 3D sketch has no frame, so it cannot ride on a fixture or mount frame, and 5.1 says sketches sit on a FrameId. Changing this after .gctrl v1 exists needs a migration. (c) No sketch-to-sketch dependency order or cycle rule. (d) Whether lines share point ids or own their endpoints joined by Coincident constraints is unstated. It decides whether a corner has a deletable coincident glyph (5.5 promises glyph hover and Delete) and what Delete and trim do. (e) Circle radius storage, standalone points, and non-deletable origin are implied only. (f) The plane convention (U, V, normal) of the Origin planes is undefined, yet 'look at sketch plane' and the default waypoint tool axis (tool Z = minus plane normal, 5.10) depend on its sign.

**Fix.** Replace the model line in 5.5 with: Sketch { space: Planar(FrameId) | Spatial(FrameId) (default World), points: Store<SkPoint>, curves, constraints, dimensions }. SkPoint { pos: Uv | Xyz, kind: Free | External(ExternalRef) }. ExternalRef = FrameOrigin(FrameId) | WorkPoint(FrameId) | SketchPoint{sketch, point} | Broken{last}. Curve = Line{a, b} | Circle{c, r: Length} | Arc{c, s, e} (CCW), each with a construction flag. 3D plane references: FramePlane{frame, XY | YZ | ZX}. Rules: an External point is a fixed parameter with provenance; its coordinates are recomputed from the source (world pose into this sketch's frame) before each solve. The projected origin is External(FrameOrigin), created on sketch entry in 2D and 3D, and cannot be deleted. Sketch dependencies (external references and driven-dimension references) form a DAG; creating a reference that closes a cycle is rejected. The update flow re-solves dependants in topological order when a source sketch or frame changes. A deleted source turns the reference into Broken{last}: it stays fixed and a warning is logged. Each curve owns distinct endpoint points; shared corners are Coincident constraints (substituted in the solver, so coordinates are bit-equal); picking a coincident class returns its lowest id. Plane convention: a planar sketch uses the frame's local XY with U = +X, V = +Y, normal = +Z. Origin plane frames: XY (U +X, V +Y, n +Z), XZ (U +X, V +Z, n -Y), YZ (U +Y, V +Z, n +X). 'Look at' places the camera looking along -n with up = V. Add a fixture: a 3D point Coincident with External(SketchPoint) follows a 2D dimension edit in the same Txn.

## 8. [MAJOR] 4.2 ('deletion cascades to referrers: constraints, dimensions, waypoints'), 3.2 (trim is P1), 5.5, 5.10

**Problem.** Trim is P1 and is in the ribbon, but the plan has no specification for it: intersection computation, which piece keeps which id, what happens to constraints and dimensions, how a circle becomes an arc. More seriously, 4.2 cascades deletion to waypoints. Trimming or deleting a line then silently deletes every waypoint on its removed endpoint and breaks the paths that use them. That is data loss in the motion layer caused by a sketch edit, and it defeats the purpose of stable ids for waypoints.

**Fix.** Change 4.2: 'Deletion cascades to constraints and dimensions. Waypoints and path segments are never cascade-deleted: a waypoint whose sketch point is deleted is converted in the same Txn to PositionSource::Explicit at its last position, marked detached, logged, and its paths are marked stale. If the deleted point has a Coincident sibling, the waypoint is retargeted to the lowest-id sibling instead.' Add a trim rule table to 5.5. (1) Intersections: line-line, line-circle, circle-circle, restricted to arc sweeps and segments, tolerance 1e-9 S, construction curves included as cutters. (2) The removed piece is the span between the nearest intersections on either side of the pick; no intersection means the whole curve is deleted. (3) Line or arc cut at one end: the curve keeps its id and its far endpoint; a new endpoint point is created with PointOnCurve(new, cutter) through try_add. (4) Middle piece removed: the original id keeps the piece containing endpoint a (start for an arc), and a new curve is created for the other piece; direction constraints (H, V, Parallel, Perpendicular, Collinear) are copied to it when try_add accepts. (5) A circle with two or more intersections is replaced by an Arc with a new curve id; the centre point id is kept, a radius dimension is transferred, and start and end are ordered so the CCW sweep covers the kept part. (6) Constraints and dimensions on a removed endpoint are deleted; those on the surviving curve are kept only if still satisfied at the current coordinates. (7) Trim is one Command and one undo step, and the solve after it must be a no-op (bit-identical coordinates). If the schedule slips, trim may move to P2, but the waypoint detach rule stays P1.

## 9. [MAJOR] 5.4 (3D constraints), 5.5 (3D sketch: active plane, Tab, axis lock), 3.1 item 4

**Problem.** How a 3D point is computed from a 2D cursor is not specified, and the degenerate cases are the common ones. The ray-plane intersection is unbounded when the active plane is nearly edge-on to the view. An axis lock is ill-conditioned when the axis points along the view direction. The first point has no 'previous point' to define the plane. Constraint-set gaps: (a) the 3D angle residual atan2(|a x b|, a.b) - theta has an undefined gradient at 0 and pi (square root of zero), the same NaN class the review banned in 2D. (b) Auxiliary unknowns t and lambda need initial values on every solve, must not be shown in mobility, colouring or 'N dimensions needed', and must not be translated or scaled by the frame. (c) With only aligned 3D distance dimensions, a general oblique point cannot be fully dimensioned without trilateration; 'point-plane distance' is listed but no plane is referencable from a 3D sketch. (d) Nothing grounds a 3D sketch, so 'fully constrained' is unreachable.

**Fix.** Add to 5.5 a pure function place_3d(ray, prev: Option<Xyz>, plane, px_scale, candidates) -> Snap3 { pos, kind, implied } with this order. (1) An existing sketch point or work point within 8 px: its exact position, implying Coincident. (2) Axis lock: for each sketch-frame axis through prev, the closest point on the axis to the cursor ray; accepted when the screen distance is <= 8 px and |axis . view_dir| < cos(10 deg); implies AlongAxis(prev, new, axis), suppressed with Ctrl. (3) Plane: ray intersected with the active principal plane through prev (through the sketch-frame origin for the first point); if |ray_dir . n| < sin(10 deg) the result is Refused(EdgeOn) with the status-bar text 'plane is edge-on: press Tab', and no point is placed; plane placement implies no constraint. Tab cycles XY, YZ, ZX of the sketch frame; the initial plane is the one whose normal is most aligned with the view direction. Add to 5.4: Angle3 values are restricted to (0, pi) exclusive, guarded when |a x b| < 1e-9 (degenerate outcome, fallback gradient), and 0 or pi is rejected in favour of Parallel. Auxiliary unknowns are ParamKind::Ratio, initialised each solve from geometry (t = (p - a).d / |d|^2, lambda = a.b / |b|^2), and excluded from mobility and colouring; DOF = n - rank still counts them. PointPlaneDistance{p, FramePlane, side, value} against the sketch frame's principal planes provides coordinate dimensions. Every 3D sketch gets the External(FrameOrigin) origin point. 3D smart dimension: line gives length, two points give distance, two lines give angle, point + origin plane gives plane distance.

## 10. [MAJOR] 5.5 (inference / snap as a pure function, priority list)

**Problem.** The snap list is not implementable as written because several kinds have no defined constraint, and one is wrong. 'Quadrant' has no matching constraint in the 13-constraint set. 'Horizontal / vertical alignment' merges two different Inventor behaviours: the segment being drawn is horizontal (creates a Horizontal constraint) versus the cursor is aligned with another point (dotted line, position only, no constraint). Parallel inference is missing although Perpendicular is present, and neither has a rule for choosing the reference line. The function signature (cursor, pixel scale, geometry) has no previous point and no hover memory, so tangent, perpendicular and H/V of the current segment cannot be computed. No pixel tolerances, no hysteresis (the snap flickers between candidates), no rule for combined snaps (horizontal and on-curve at once). Arc midpoints cannot be constrained (Midpoint is line-only).

**Fix.** Replace the priority sentence with a table (snap kind: condition: implied constraints). Point or endpoint, 8 px: Coincident. Centre, 8 px: Coincident with the centre point. Midpoint, lines only: Midpoint. Intersection of two curves: PointOnCurve twice. Quadrant: position only plus PointOnCircle. Tangent (the segment ends on a circle or arc and is tangent): PointOnCurve + Tangent with the captured side. Perpendicular or Parallel to a reference line: that constraint. On curve, 6 px (within the segment or arc sweep): PointOnLine or PointOnCircle. Current segment horizontal or vertical (within 4 px at the cursor): Horizontal or Vertical on the new line. Point alignment (cursor level with an existing point): position only, no constraint. Grid: none. Combination rule: one positional snap plus at most one directional snap, the position being the intersection of the direction ray with the target. Hysteresis: the current snap is kept until the cursor leaves 1.5 times its tolerance. Signature: snap(cursor, px_scale, geometry, ctx: SnapCtx { prev_point, drawing: Option<CurveKind>, memory: InferenceMemory (the last 3 hovered curve ids, the reference lines for Parallel and Perpendicular), suppress: bool }) -> SnapResult. All implied constraints are applied through try_add in table order and dropped unless Added. Rectangle tool output: 4 lines, 4 Coincident, H, V, H, V; expected DOF 4.

## 11. [MINOR] 4.1 (gc_linalg), 6 Stage 1 and Stage 2 gates, 8 (risks), profile settings

**Problem.** gc_linalg is frozen in Stage 1, before the solver agent starts, but its listed API (column-pivoted QR with rank, null space and least squares) does not include what 5.4-5 needs. 'Class-blocked pivoted QR of J^T' is a restricted pivot strategy (pivot inside the current class block, age as tie-break), not standard global pivoting. The null basis and per-parameter mobility need explicit trailing columns of Q. The dependent-row coefficients need a solve with R11. Without these the solver agent must edit another crate, which the parallel-work rule forbids. There is also no performance gate: the review (A14) estimated about 1e8 flops per LM iteration at 300 unknowns and asked for a benchmark at 50 / 100 / 300 before any promise. The dev profile compiles workspace crates at opt-level 1, where a dense Householder QR with bounds checks will make drag scenario tests very slow.

**Fix.** Add to the gc_linalg row and the Stage 1 gate: qr(A) unpivoted for the LM stack [J; sqrt(lambda) I] (full column rank by construction); qr_pivoted(A, PivotPolicy::Global | Blocked { block_ends: &[usize] }, rel_tol) -> { rank, perm, r_diag }, where Blocked pivots only inside the current block until its largest remaining column norm falls below rel_tol * |R_11|, then moves on, ties to the lowest index; apply_qt; q_columns(range), with the null basis being columns rank..n of Q from the QR of J^T and mobility being the row norm of that basis; solve_r11 for the coefficients; lstsq_min_norm. The Jacobi SVD is not used by the solver; it is the test oracle. Property test: QR rank equals SVD rank on random rank-deficient matrices and on a Kahan matrix. Add to the root profile: [profile.dev.package.gc_linalg] and [profile.dev.package.gc_solver] opt-level = 3. Add a Stage 2 gate: warm-started component solve plus diagnosis at 50 / 100 / 300 unknowns, reported in release; target one drag frame <= 4 ms at 100 unknowns. If 300 unknowns exceeds 16 ms: a drag re-solves only the grabbed component, and diagnosis runs on drag end and on structural change only.

## 12. [MAJOR] Appendix C (F1-F20), 5.4 acceptance line, 6 Stage 2/3/5 gates, 7

**Problem.** F1-F20 are all 2D solver-kernel fixtures. Nothing tests 3D constraints or auxiliary unknowns, substitution blame, multi-row partial redundancy, expressions and driven dimensions, external references, idempotence, trim, or the sketch layer's policies, and the UI scenario list in section 7 has one sketch line. The oracle crates are 'optional', but Cargo.lock is frozen in Stage 0, so the decision must be made now. ## Verdict

The solver section adopts the adversarial review's P0 list in name and gets the core pipeline right, but it is a summary, not a specification. Two points would fail as written. First, the drag objective: I reproduced that an exact pin alone still rotates the F16 triangle by 4.5 to 7 degrees; only a tie-break anchored at the drag-start state gives 0. Second, per-frame drag commits contradict the one-Txn-per-frame, commands-are-data model and would flood the undo history and invalidate every robot cache on each mouse move. Beyond those, the plan leaves undefined exactly the things parallel agents will each invent differently: tolerances and the nudge direction (a rigid-motion nudge gives a false conflict, also reproduced), what try_add means once constraints are substituted or carry several rows or auxiliary unknowns, what each dimension stores to keep its branch, what the document contains after a failed solve, and how driven dimensions enter the dependency graph. The sketch data model lacks external references, a frame for 3D sketches and an endpoint-ownership rule; it also cascades deletion into waypoints, which silently destroys motion data on trim. 3D point placement, the snap-to-constraint mapping and trim have no rules at all, and the acceptance suite tests none of the 3D, substitution, expression or sketch-layer behaviour. None of this requires reopening a fixed decision. With the twelve corrections written into sections 4.2, 5.1, 5.4, 5.5 and Appendix C, the in-house solver and the Inventor-style sketcher are buildable in M1; without them I expect F16 to fail, undo and staleness to misbehave during drags, and Stage 3 to stall on interface disagreements between gc_solver, gc_sketch, gc_doc and gc_tools. Nothing was compiled; the two numerical claims come from a numpy model with finite-difference Jacobians.
