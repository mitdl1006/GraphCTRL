## 3. [MAJOR] 6 Stage 0 gate, 7 (GPU/UI tests), 8 (SwiftShader risk), 5.2

**Problem.** The fallback chain does not end in an executable state. Verified today: egui_kittest 0.37 wgpu.rs builds its render state with `.expect("Failed to create render state")`, so without an adapter every `.wgpu()` harness panics; `apt-cache policy mesa-vulkan-drivers` currently reports 'Candidate: (none)', so the lavapipe fallback is unproven; 'demote GPU tests to CI only' has no mechanism and CI may be un-pushable (section 8) and is not observable from the sandbox. Stage 4 and 5 gates are purely 'kittest + snapshots', so in that outcome they have no evidence at all. The research recommendation 'let Viewport3d tolerate a missing RenderState so logic tests run without a GPU' (bm8miguoz.txt, Recommendation 3) was dropped from the plan. The ICD path in section 7 is specific to this image (chromium-1243); if an agent puts VK_ICD_FILENAMES into .cargo/config.toml [env] the owner's machine loses all Vulkan drivers. kittest also never exercises winit, surface creation, real fonts or eframe startup.

**Fix.** Add to 5.2 and 7: 'GPU is optional by construction. gc_viewport and gc_app must run when cc.wgpu_render_state is None (viewport shows a placeholder; all tools, picking, commands and panels still work because picking is CPU-side). Scenario tests assert document state through a harness built WITHOUT .wgpu(); only snapshot tests need a GPU.' Add a dev crate gc_test_support with `fn gpu() -> Option<GpuCtx>` that probes an adapter before any kittest wgpu harness is built; with GC_REQUIRE_GPU=1 (set by `cargo xtask test-gpu` in the sandbox and in CI) a missing adapter is a test failure, otherwise the test prints SKIPPED(no adapter). `cargo xtask test-gpu` discovers the ICD by glob (/opt/pw-browsers/chromium-*/chrome-linux*/vk_swiftshader_icd.json) and sets the variables for the child process only; committing VK_ICD_FILENAMES or WGPU_BACKEND to .cargo/config.toml is forbidden. GPU tests live in dedicated integration-test binaries run with --test-threads=1 (kittest's GPU wait timeout is 10 s; a CPU rasteriser with 4x MSAA under 4-way test parallelism will flake). Stage 0 gate becomes three explicit proofs with recorded output: (1) gc_render clear+readback pixel assert, (2) a kittest wgpu snapshot of the minimal app, (3) a real-binary smoke run `xvfb-run -a graphctrl --smoke-frames 5 --screenshot out.png` (the SwiftShader library exports VK_KHR_xcb_surface and VK_EXT_headless_surface; libxkbcommon and Xvfb are present) — if (3) fails it is recorded as 'owner PC only', not silently dropped. If (1)/(2) fail and lavapipe cannot be installed, Stage 4/5 gates switch to: scenario tests without GPU + naga validation + the owner's manual checklist, and that fact is stated at the top of the final report.

## 4. [MAJOR] 7 (GPU/UI and scenario tests), Appendix A (egui_kittest), 5.2, 5.9, 5.10

**Problem.** kittest semantics are under-specified for an app with animations, playback and jobs. Verified in egui_kittest-0.37.0/src/lib.rs: run() stops as soon as no IMMEDIATE repaint is requested (repaint_delay != 0), so request_repaint_after and a worker thread's later Notifier call are not awaited; step_impl only sets predicted_dt = step_dt (0.25 s) and the defaults are max_steps = 4, so a view transition or timeline that uses std::time::Instant never settles or is nondeterministic, and playback (repaints every frame) panics in run(). Snapshot determinism rules are missing: default threshold 0.6 and 0 failed pixels, output path tests/snapshots per crate, a single baseline per name — baselines produced on SwiftShader will not match lavapipe or WARP in the 3D region, while section 7 puts the same tests in Windows/Linux CI. Appendix A/research cite SnapshotOptions::failed_pixel_count_threshold, which is deprecated since 0.36 (renamed max_failed_pixels) and will not compile under the planned #![deny(deprecated)]. Missing-glyph policy is Panic and label lookups depend on the UI language (sys-locale). InlineExecutor makes progress and cancel UI untestable. Nothing stops an agent from running UPDATE_SNAPSHOTS=1 to make a failing test pass.

**Fix.** Add a 'UI test rules' block to section 7: (1) All animation, playback and debounce timing reads egui input time (ctx.input(|i| i.time / i.stable_dt)); std::time::Instant/SystemTime are banned in ui/app/gc_session via clippy disallowed-types, except in gc_jobs statistics. (2) Use run() only when the UI must settle; during playback or job progress use run_steps(n); a test helper pump_until(|app| cond, max_steps) is the only allowed waiting loop. (3) gc_jobs gains ManualExecutor (test-driven: advance one progress tick, complete, or cancel) next to InlineExecutor; the app receives its Executor by injection. (4) Every harness fixes size 1280x800, pixels_per_point 1.0, light theme, locale forced to ko (never sys-locale) and bundled Pretendard only; widgets are found by tr!(key) or command id, never by string literals. (5) Reference renderer is SwiftShader: gc_test_support::snapshot() compares strictly when the adapter name contains 'SwiftShader' and otherwise writes .new/.diff PNGs as CI artifacts without failing; 3D correctness is asserted numerically (pixel classes at projected points, readback depth) on every renderer. (6) Use max_failed_pixels; one kittest.toml at the workspace root. (7) A unit test iterates every i18n catalogue string in both languages and asserts the bundled font has all glyphs. (8) Any baseline update must be listed in the stage report with a one-line statement of what was visually verified in the PNG; unreviewed UPDATE_SNAPSHOTS is a gate failure.

## Verdict

The technical content of the plan is strong, but as a delivery document it is not yet executable by agents: the stage table contains a real ordering defect (gc_doc and gc_persist are scheduled before the types they depend on, and the document-to-scene glue has no owner), the only place the whole scenario is ever exercised is a single monolithic Stage 5 behind a GPU path that is still unproven in this sandbox (lavapipe has no apt candidate today and kittest panics without an adapter), and the gates mostly name test categories rather than checkable evidence. Most importantly for the owner's request, no gate proves planning on anything other than UR5e, so 'URDF-driven, high-quality manipulator planning' could be declared done without a single non-UR trajectory; and the quality thresholds are wall-clock numbers that contradict the plan's own determinism rule and cannot be run inside the per-stage test command. The scope (about 29 crates) is deliverable only if it is re-cut into vertical slices with an explicit cut order: add a headless gc_session crate and a headless scenario gate at the end of Stage 3, make the app GPU-optional, split Stage 5 into gated sub-stages ordered shell -> 2D sketch -> robot/planning -> 3D sketch -> plumbing, move trim, CIRC, PRM*, TCP-row TOPP-RA and layout persistence to P2, promote the generic-URDF gate, the other three UR data packages and a minimal TCP-sphere mode to P1, add a Windows cross-check and a single `cargo xtask gate`, and copy the plan and research into the repository. With those changes written in, I would approve execution; without the first two issues fixed, I would not.
